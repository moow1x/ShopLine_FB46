Три варіанти некоректного Quantity вказують на один дефект BUG-002 і мають той самий Bug ID. BUG-005 — дослівна косметична розбіжність (фінальна крапка). Норматив 10 звітів досягнуто за буквального зіставлення текстів SRS. КТ має узгодити, чи зараховуються косметичний BUG-005 та брендування демо BUG-006 за GUI-10. Якщо викладач приймає відповідну відмінність як виняток, для нормативу потрібен підтверджений замінник. Тлумачення §12 щодо трьох failed-кейсів, пов’язаних з одним BUG-002, варто звірити з КТ: окремі набори даних фіксуються окремо, звіти про один прояв не дублюються. Підказка «files must be 0kb» зафіксована як напрямок додаткової перевірки, поза цим числом. Для перевірки фактичної поведінки потрібне рішення щодо ED-11 та безпечний тестовий прогін з власним вкладенням.

## Що потрібно для закриття Definition of Done

1. КТ підтверджує розподіл, межі спринту, винятки з покриття й пріоритети. Для спірних очікувань потрібно уточнити застосовність ED-01, ED-08/09, ED-11, ED-22, ED-24 залежно від сценарію.
2. ТА виправляє тест-кейси за рецензією. ІТ готує власний тестовий профіль, проводить прогін на поточній збірці, завершує доступні blocked/skipped і документує решту з погодженням КТ. Для повторного прогону записати фактичного виконавця, браузер, версію, ОС, час і збірку.
3. СМ веде таблицю задач і standup, рецензує всі кейси за §5.3 і звіти за §4.10–4.11, готує команду до бліцу. Дату й підпис ставить після фактичної перевірки, а статус reviewed — після усунення зауважень.
4. АО незалежно відтворює три звіти різних severity тільки за текстом. Заповнює audit.md перед демо.
5. Команда проводить демо і Start/Stop/Continue. СМ заповнює retro.md за фактичним обговоренням. КТ оновлює статистику та збирає інкремент.
